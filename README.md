<a id="overview"></a>

## 🔎 Overview

**DRBenchPro measures structured knowledge coverage in deep research reports.**
It evaluates how comprehensively an agent covers major research directions and
how far it follows chains of related knowledge within those directions.

Starting from Wikipedia root entities, we build local knowledge trees and sample
research scopes. Each sampled tree generates both a research query and a set of
evidence-grounded rubrics. Agents receive **only the query**; the reference tree
and rubrics are reserved for evaluation. Keeping the rubric topology makes
coverage strengths and omissions interpretable through three metrics:

| Metric | What it measures |
| --- | --- |
| **Breadth** | Coverage across the selected research directions |
| **Depth** | Coverage along related knowledge chains |
| **Overall Coverage** | The geometric mean of case-level Breadth and Depth |

This repository provides the frozen benchmark, Judge prompts, report evaluator,
structural metrics, benchmark construction code, and the optional
**DRBenchPro Local Research Framework**. You can evaluate reports generated by
your own model or research system independently of the bundled framework.

<a id="benchmark"></a>

## 🧩 Benchmark

| Item | Value |
| --- | --- |
| Domains | **24** |
| Root entities | **48** — two per domain |
| Research cases | **144** — six per domain |
| Evidence-grounded rubrics | **44,102** |
| Rubrics per case | **236–310** |
| Research directions per case | **10** |
| Maximum rubric depth | **3 hops** |
| Evaluated agent configurations in the paper | **16** |

<p align="center">
  <img src="assets/readme/construction.webp?v=622c0cd496d0" alt="DRBenchPro pipeline: Wikipedia-derived local trees, subgraph sampling, shared query and rubric construction, and topology-aware Breadth/Depth/Overall evaluation." width="1000">
</p>

The dataset is included in this GitHub repository as **uncompressed UTF-8
JSONL**, and is also available on
[Hugging Face](https://huggingface.co/datasets/zhuiluozhiji/DRBenchPro).
Cloning this repository already provides the complete benchmark; no additional
dataset download is required.

| File | Intended use | Fields |
| --- | --- | --- |
| [queries.jsonl](data/benchmark/queries.jsonl) | Input to the model producing reports | `case_id`, `query` |
| [cases.jsonl](data/benchmark/cases.jsonl) | Reference material for the evaluator | `case_id`, `query`, `domain`, `rubrics` |
| [registry.json](data/registry.json) | Dataset identity and file integrity | File paths and SHA-256 checksums |

Each rubric contains `rubric_id`, `rubric_text`, `rubric_depth`,
`parent_rubric_id`, `source_title`, and `target_title`. Parent references preserve
the tree used for structural scoring. See the [dataset guide](data/README.md)
for the complete schema, data license and attribution.

For HF preview, Python loading, or a separate JSONL download, see
[get the benchmark](data/README.md#get-the-benchmark). The HF `queries` and
`cases` configurations both use the `test` split. The original JSONL files are
identical to the bundled files and can be checked with `verify-data`.

**Keep the evaluator's rubrics and reference trees hidden from the model
generating the report.** Use `queries.jsonl` for report generation and
`cases.jsonl` for evaluation.

The paper evaluates **16 agent configurations across all 144 cases**: three
Deep Research Systems, six Native Search LLMs, and seven backbone LLMs under
the Local Research Framework. Claude Opus 5 achieves the highest Overall
Coverage (**57.04%**). Breadth and Depth expose different research profiles;
the same backbone can also behave differently under different research workflows.

<a id="quick-start"></a>

## 🚀 Quick Start

<a id="install"></a>

### 📦 Install

Use **Python 3.11+** on Linux or macOS. On Windows, use WSL2 or Docker for
the evaluation and research runners, which require POSIX file locks.

```bash
git clone https://github.com/ZJU-REAL/DRBenchPro.git
cd DRBenchPro
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e .
drbenchpro --help
```

The base installation is sufficient for report evaluation and metrics.
All commands below run from the repository root.

<a id="try-the-offline-example"></a>

### 💻 Try the offline example

Verify the bundled data and compute metrics from the supplied synthetic scores:

```bash
drbenchpro verify-data --registry data/registry.json
drbenchpro validate --cases data/benchmark/cases.jsonl
drbenchpro metrics --cases examples/evaluator_case.json \
  --scores examples/rubric_scores.jsonl --output outputs/example-metrics.json
```

The example returns Breadth `0.84`, Depth `0.4375`, and Overall
`0.6062177826491071`. These are synthetic demonstration results. This example
requires no model credentials, network access, or Wikipedia service.

<a id="evaluate-your-own-model"></a>

## 🧪 Evaluate Your Own Model

<a id="1-generate-reports-from-the-queries"></a>

### 📝 1. Generate reports from the queries

Give each query in `data/benchmark/queries.jsonl` to your model or research
system. Save the complete reports to `my-reports.jsonl`, using the exact
`case_id` from each query and a `system_id` identifying your system:

```json
{"case_id":"d01_adult__r05_fanny_hill__s01","system_id":"my-model","report":"Your complete generated report..."}
```

One line represents one report. JSON-encode newlines inside the `report` string;
Markdown and citations are supported. A full evaluation has one report per case
for each system. Multiple systems can share one report file if their `system_id`
values differ. See the [report format and examples](examples/README.md).

<a id="2-configure-the-judge"></a>

### ⚙️ 2. Configure the Judge

Configure an OpenAI-compatible **Chat Completions** endpoint in your shell:

```bash
cp .env.example .env
# Fill in JUDGE_API_KEY, JUDGE_BASE_URL and JUDGE_MODEL in .env.
source .env
```

The paper uses **Gemini 2.5 Pro** as Judge. Set `JUDGE_MODEL` to the model ID
accepted by your provider and keep Judge settings consistent when comparing
systems. Other compatible Judges can be used, but their scores need not match
the paper. Model calls may incur provider charges.

<a id="3-validate-and-evaluate"></a>

### ✅ 3. Validate and evaluate

```bash
drbenchpro validate-reports --cases data/benchmark/cases.jsonl \
  --reports my-reports.jsonl --require-full
drbenchpro preflight --stage evaluate --cases data/benchmark/cases.jsonl \
  --reports my-reports.jsonl --output outputs/my-evaluation --offline
drbenchpro evaluate --cases data/benchmark/cases.jsonl \
  --reports my-reports.jsonl --output outputs/my-evaluation
```

Validation and offline preflight make no model calls; `evaluate` calls your Judge.
This workflow does not require the Local Research Framework, a Wikipedia service,
a GPU, or Docker. The installed configuration sends the complete report and
rubrics, with smaller-chunk fallback if needed.

The formal CLI uses
[`report_scoring_final_score_only-half.md`](src/drbenchpro/resources/prompts/evaluation/report_scoring_final_score_only-half.md):
an English template requesting **`rubric_id` and `score`, without `reason`**.
Scores are `1` (Satisfied), `0.5` (Partially Satisfied), or `0` (Not Satisfied).
The optional `score_reason_half` Python API adds reasons; see the
[evaluation guide](src/drbenchpro/evaluation/README.md#reason-output-python-api).

<a id="4-compute-metrics-and-export-results"></a>

### 📐 4. Compute metrics and export results

```bash
drbenchpro metrics --cases data/benchmark/cases.jsonl \
  --scores outputs/my-evaluation/scores.jsonl \
  --output outputs/my-evaluation/metrics.json \
  --csv outputs/my-evaluation/systems.csv \
  --case-csv outputs/my-evaluation/cases.csv
```

**Structural metrics map only score `1` to covered; both `0.5` and `0` are
uncovered**, following the paper's binary coverage definition. Breadth and Depth
are aggregated over the actual rubric tree; case Overall Coverage is
`sqrt(Breadth × Depth)`. JSON and CSV metrics use the **0–1 scale**; the paper
table above displays percentages. See the [metric definitions](src/drbenchpro/metrics/README.md).

| Output | Contents |
| --- | --- |
| `scores.jsonl` | Validated rubric scores for completed case/system reports |
| `checkpoint.json` | Completed reports, scores, failures, and resume identity |
| `run.json` | Configuration, coverage, progress, and available usage statistics |
| `metrics.json` / `systems.csv` | Per-system Breadth, Depth, and Overall Coverage |
| `cases.csv` | Per-case metric breakdowns |

<details>
<summary><strong>🔄 Resume, partial evaluation, and reproducibility</strong></summary>

Repeat the evaluation command with the same inputs and settings plus `--resume`:

```bash
drbenchpro evaluate --cases data/benchmark/cases.jsonl \
  --reports my-reports.jsonl --output outputs/my-evaluation --resume
```

Completed reports are reused; failed or unfinished reports are retried. Changing
case material, report text, Judge settings, or the composed prompt requires a new
output directory. Missing reports and failed Judge calls are recorded explicitly
and never converted to zero scores.

For an explicitly partial run, omit `--require-full` and add `--allow-subset` to
`metrics`. The output records actual and expected case counts. Keep dataset
identity, Judge configuration, prompts, and metric parameters consistent for
comparisons. The metric contract is `drbenchpro-coverage-v1` with
`beta=0.60, alpha=0.25, eta=0.75, rho=0.50`.

Record Python and dependency versions with results. Cross-version floating-point
differences can occur in the last digits, so compare numerical results with a
tolerance. Optional `--input-usd-per-million` and `--output-usd-per-million` flags
provide a cost estimate when provider usage is available.

</details>

<a id="local-research-framework"></a>

## 🛠️ Local Research Framework

For a controlled research environment, the optional framework uses a fixed
English Wikipedia snapshot and a shared **Planner → Research Units → Gap
Analysis → Synthesis** workflow. Backbones use the same Search/Open interface
and tool budgets. The implementation and selected model profiles are included.

<p align="center">
  <img src="assets/readme/research-framework.webp?v=9fb172248558" alt="Local Research Framework: a planner creates research units, units collect grounded Wikipedia evidence, a gap check may request further research, and synthesis produces the report." width="1000">
</p>

The prebuilt
[**DRBenchPro Local Research Framework — Docker Image**](https://huggingface.co/datasets/zhuiluozhiji/DRBenchPro-runtime)
includes the application, benchmark, and fixed Wikipedia index. The public HF
repository provides download parts and verified import helpers; it does not run
the service online. Follow the
[download, verify, and import quickstart](docker/README.md#download-the-framework-image)
to run it with Docker, without rebuilding the index or installing the framework
in a host Python environment. You still supply your own model and Judge APIs.

For a source-based setup, install the optional dependencies and copy the configurations:

```bash
python -m pip install -e '.[local-research]'
drbenchpro init-config --output configs
```

Prepare and start the Wikipedia service using the
[Wikipedia setup guide](src/drbenchpro/local_research/wikipedia/README.md), then
set `MODEL_API_KEY`, `MODEL_BASE_URL`, and `MODEL_NAME`, and check `wiki.base_url`
in `configs/local_research.yaml`. Generate one report:

```bash
drbenchpro research --queries data/benchmark/queries.jsonl \
  --config configs/local_research.yaml --limit 1 --system-id my-model \
  --output outputs/research-one
```

The resulting `reports.jsonl` uses the same interface as external reports.
Evaluate it with `--reports outputs/research-one/reports.jsonl`; for this one-case
run, use `--allow-subset` when computing metrics. Remove `--limit 1` to generate
all 144 reports. See the [framework guide](src/drbenchpro/local_research/README.md)
for model profiles, budgets, case selection, and resume.

The [container guide](docker/README.md) covers running the published framework
image and building your own image. The application-only image uses an external
Wikipedia index; the published framework image embeds it. Report evaluation
remains available without either image.

<a id="construct-new-cases"></a>

## 🏗️ Construct New Cases

The construction pipeline creates new Wikipedia-derived research tasks:

```bash
python -m pip install -e '.[construction]'
drbenchpro construct --seed 'Ada Lovelace' --output outputs/new-cases
```

Construction performs online Wikipedia fetches and model calls, using `MODEL_*`
credentials. New cases built from live Wikipedia are a separate dataset from
the frozen benchmark. See the [construction guide](src/drbenchpro/construction/README.md).
